    01 Зачем нужен Kubernetes

    Первый вопрос почти всегда «что это и зачем». Нужен короткий уверенный ответ.

    Проблема, которую он решает

    Контейнер упаковывает приложение со всеми зависимостями. Запустить один контейнер на одной машине просто: docker run. Сложности начинаются, когда сервисов десятки, машин сотни, и нужно:

    • решать, на какую машину поставить контейнер, чтобы хватило CPU и памяти;
    • перезапускать упавшее и переносить работу с умершей машины;
    • обновлять версии без простоя и откатывать неудачные;
    • дать сервисам находить друг друга, когда IP контейнеров постоянно меняются;
    • масштабироваться под нагрузку, подключать диски, раздавать конфиги и секреты.

    Kubernetes (K8s) — оркестратор контейнеров: платформа, которая превращает группу машин в один пул ресурсов и сама поддерживает приложения в описанном состоянии.

    Главная идея: декларативность и цикл согласования

    Вы не говорите «запусти 3 контейнера» (императивно). Вы записываете желаемое состояние: «должно быть 3 реплики образа api:1.4». Дальше контроллеры в бесконечном цикле сравнивают желаемое состояние с фактическим и устраняют разницу. Этот цикл называют reconciliation loop (цикл согласования, или control loop).

    for {
  desired := read(spec)     // что хотим
  actual  := observe(world) // что есть
  if diff(desired, actual) { act() }  // приблизить actual к desired
}
    Почему это важноИз этой идеи вытекает почти всё поведение Kubernetes: самовосстановление (под умер → разница → создать новый), идемпотентность (kubectl apply можно повторять), устойчивость к сбоям (контроллер перезапустился → перечитал состояние → продолжил). Система level-triggered: она реагирует на текущее состояние, а не на пропущенные события. Если контроллер пропустил событие, он всё равно увидит расхождение при следующем проходе.

    Что Kubernetes делает, а что нет

    Делает

    • Планирование контейнеров по узлам
    • Самовосстановление и перезапуски
    • Service discovery и балансировка
    • Rolling update и откат
    • Автомасштабирование
    • Подключение хранилищ
    • Конфиги и секреты
    • RBAC и изоляция по namespace

    Не делает сам

    • Не собирает образы (это CI)
    • Не даёт готовый логинг и мониторинг
    • Не реализует сеть сам: это делает плагин CNI
    • Не реализует диски сам: это делает драйвер CSI
    • Не PaaS: нет «git push → прод» из коробки
    • Не делает stateful-приложение отказоустойчивым автоматически

    Контейнер ≠ виртуальная машина

    Контейнер — обычный процесс Linux, изолированный механизмами ядра:

    • namespaces — что процесс видит: свои PID, сеть, mount, hostname, IPC, пользователи;
    • cgroups — сколько процесс может потребить: CPU, память, I/O. На cgroups построены requests и limits в Kubernetes;
    • файловая система из слоёв образа (overlayfs).

    Ядро общее для всех контейнеров на узле. Поэтому контейнеры лёгкие, но изолированы слабее, чем ВМ.

    Ответ на 30 секунд«Kubernetes — платформа оркестрации контейнеров. Я декларативно описываю желаемое состояние в манифестах, API-сервер сохраняет его в etcd, а набор контроллеров постоянно приводит фактическое состояние кластера к желаемому: планирует поды на узлы, перезапускает упавшие, делает rolling update, балансирует трафик через Service, масштабирует. Всё взаимодействие идёт через API-сервер, а компоненты слабо связаны и общаются через watch на изменения объектов».

    02 Архитектура кластера

    Самая важная часть. Нужно уметь нарисовать схему и рассказать роль каждого компонента.

    Control plane

    КомпонентЧто делаетВажные детали
    kube-apiserverREST API кластера. Принимает запросы, проводит аутентификацию, авторизацию и admission, валидирует и пишет объекты в etcd. Раздаёт watch-потоки изменений.Без состояния, масштабируется горизонтально за балансировщиком. Единственный компонент, который обращается к etcd. Все остальные, включая kubelet и scheduler, общаются только с ним.
    etcdРаспределённое key-value хранилище. Здесь лежит всё состояние кластера: объекты, их spec и status.Консенсус Raft, строгая согласованность. Кворум — большинство узлов. Обычно 3 или 5 членов. Потеря etcd без бэкапа означает потерю кластера.
    kube-schedulerНаходит поды без узла (spec.nodeName пуст) и выбирает для каждого узел.Сам ничего не запускает. Только записывает привязку (binding) через API. Работает в два шага: фильтрация, затем оценка.
    kube-controller-managerОдин процесс, в котором крутятся десятки контроллеров: Deployment, ReplicaSet, StatefulSet, DaemonSet, Job, Node, EndpointSlice, Namespace, ServiceAccount, GC и другие.При нескольких копиях активна одна: выбор лидера через объект Lease.
    cloud-controller-managerИнтеграция с облаком: создаёт балансировщики для Service type=LoadBalancer, узнаёт об удалении ВМ, настраивает маршруты.В on-prem кластере его может не быть. Тогда LoadBalancer обеспечивает, например, MetalLB.

    Worker node

    КомпонентЧто делает
    kubeletАгент на каждом узле. Следит через watch за подами, назначенными на его узел, и запускает их через container runtime. Выполняет пробы, монтирует тома, отправляет статус подов и узла в API. Heartbeat узла — обновление объекта Lease в namespace kube-node-lease примерно каждые 10 секунд.
    container runtimecontainerd или CRI-O. kubelet общается с ним по интерфейсу CRI (gRPC). Docker как runtime (dockershim) удалён в версии 1.24. Образы, собранные Docker, работают: это стандартные OCI-образы.
    kube-proxyРеализует Service: программирует на узле правила iptables, IPVS или nftables, которые переводят виртуальный ClusterIP в IP реальных подов. Через себя трафик не пропускает. Некоторые CNI, например Cilium на eBPF, полностью заменяют kube-proxy.
    CNI-плагинCalico, Cilium, Flannel и другие. Выдаёт поду IP и обеспечивает связность между узлами. Часто реализует NetworkPolicy.

    Аддоны

    CoreDNS (DNS-имена сервисов), metrics-server (метрики для HPA и kubectl top), Ingress или Gateway-контроллер, CSI-драйверы.

    Ключевой архитектурный принцип: hub-and-spokeAPI-сервер в центре. Компоненты не вызывают друг друга напрямую. Scheduler не говорит kubelet «запусти под». Он записывает nodeName в объект Pod. kubelet через watch видит, что на его узел назначен под, и запускает его. Компоненты связаны только через общее состояние. Поэтому любой из них можно перезапустить, заменить или дописать свой (оператор), не трогая остальные.

    03 Что происходит после kubectl apply

    Классический вопрос: «Опиши, что происходит от kubectl apply до запущенного контейнера». Он проверяет, что вы понимаете этапы 1 и 2 в связке.

    Применяем Deployment с replicas: 3:

    1. kubectl читает kubeconfig (адрес API, учётные данные), отправляет HTTPS-запрос в API-сервер. При apply вычисляется patch относительно текущего объекта. В современных версиях это обычно server-side apply с учётом владельцев полей (managedFields).
    2. Аутентификация: кто вы? Клиентский сертификат, bearer-токен, OIDC, токен ServiceAccount.
    3. Авторизация: можно ли вам выполнить create deployments в этом namespace? Обычно проверку выполняет RBAC.
    4. Mutating admission: плагины и вебхуки могут изменить объект. Например, проставить значения по умолчанию, внедрить sidecar (так делает Istio), добавить метки.
    5. Валидация схемы, затем validating admission: вебхуки и ValidatingAdmissionPolicy на CEL, Pod Security Admission, ResourceQuota. Здесь можно только отклонить запрос, но не изменить.
    6. Запись в etcd. Объект получает resourceVersion. Клиенту возвращается ответ. На этом kubectl закончил работу: дальше всё асинхронно.
    7. Deployment controller через watch видит новый Deployment и создаёт ReplicaSet с хешем шаблона пода в имени.
    8. ReplicaSet controller видит ReplicaSet с 3 желаемыми репликами и 0 фактическими, создаёт 3 объекта Pod. У подов пока нет nodeName, они в статусе Pending.
    9. Scheduler видит неназначенные поды. Для каждого фильтрует узлы, оценивает подходящие и записывает binding, то есть nodeName.
    10. kubelet на выбранном узле видит «свой» под. Через CRI создаёт pod sandbox (pause-контейнер, который держит сетевой namespace). CNI выдаёт IP. Подключаются тома (CSI), скачиваются образы, запускаются init-контейнеры, затем основные.
    11. kubelet выполняет пробы и обновляет status пода: Running, затем Ready.
    12. EndpointSlice controller видит готовый под, подходящий под селектор Service, и добавляет его IP в EndpointSlice. kube-proxy на всех узлах обновляет правила. Под начинает получать трафик.

    Механика, которая делает это надёжным

    • Watch и informers. Контроллеры не опрашивают API в цикле. Они один раз делают LIST, затем держат WATCH-поток изменений и локальный кеш. При разрыве переподключаются с последнего resourceVersion. Если история уже сжата (ошибка 410 Gone), делают LIST заново.
    • Оптимистичная блокировка. Каждое обновление содержит resourceVersion. Если объект успел измениться, API вернёт 409 Conflict, и клиент перечитает объект и повторит. Распределённых блокировок нет.
    • spec и status. spec пишет пользователь (что хочу). status пишут контроллеры и kubelet (что есть). У status отдельный подресурс API.
    • ownerReferences и сборка мусора. Pod принадлежит ReplicaSet, ReplicaSet принадлежит Deployment. При удалении Deployment сборщик мусора каскадно удаляет зависимые объекты.
    Частая ошибка на собеседованииГоворить, что «API-сервер отправляет команду kubelet запустить под» или что «scheduler запускает контейнер». Правильно: все пишут и читают объекты через API-сервер, а действуют, когда замечают изменения через watch. Исключения, когда API-сервер сам идёт в kubelet: kubectl logs, exec, port-forward.

    04 Объекты и рабочие нагрузки

    Нужно знать, какой контроллер когда выбирать и чем они отличаются.

    Анатомия любого объекта

    apiVersion: apps/v1          # группа/версия API
kind: Deployment             # тип
metadata:
  name: api
  namespace: shop
  labels: { app: api, tier: backend }
  annotations: { ... }       # произвольные данные, не для выборки
spec: { ... }                # желаемое состояние
status: { ... }              # фактическое состояние (пишет система)
    • Labels и selectors — основной способ связывания. Service находит поды по меткам. ReplicaSet считает «свои» поды по меткам. Это слабая связь: никаких жёстких ссылок по ID.
    • Namespace — логическое разделение: имена, RBAC, квоты, NetworkPolicy. Это не граница безопасности сама по себе и не сетевая изоляция по умолчанию. Узлы, PV, ClusterRole, StorageClass не принадлежат namespace.

    Pod — минимальная единица

    Pod — один или несколько контейнеров с общей сетью (один IP, общий localhost, общие порты) и общими томами. Они всегда размещаются вместе на одном узле. Pod эфемерен: не «чинится» и не переезжает. Если под умер, контроллер создаёт новый, с новым именем и IP. Отдельные поды почти никогда не создают вручную.

    Контроллеры рабочих нагрузок

    ОбъектДля чегоКлючевые свойства
    ReplicaSetДержать N одинаковых подовНапрямую почти не используется, им управляет Deployment
    DeploymentStateless-сервисыУправляет ReplicaSet: при смене шаблона создаёт новый RS и постепенно переводит реплики. Хранит историю для отката (revisionHistoryLimit). Поды взаимозаменяемы, имена случайные.
    StatefulSetБазы, очереди, кластеры с идентичностью узловСтабильные имена (db-0, db-1), стабильные DNS-имена через headless Service, свой PVC на каждую реплику (volumeClaimTemplates). По умолчанию поды создаются и удаляются по порядку. Гарантирует, что одновременно существует не больше одного пода с данной идентичностью.
    DaemonSetОдин под на каждом (или выбранном) узлеАгенты логов и метрик, CNI, CSI-node. Новый узел получает под автоматически.
    JobЗадача до завершенияcompletions, parallelism, backoffLimit, activeDeadlineSeconds. Под с restartPolicy: OnFailure или Never.
    CronJobJob по расписаниюconcurrencyPolicy: Allow, Forbid или Replace. startingDeadlineSeconds. Кластер не гарантирует ровно один запуск: задача должна быть идемпотентной.
    Deployment или StatefulSet?Если реплики взаимозаменяемы и данные хранятся снаружи — Deployment. Если каждой реплике нужны своё постоянное имя и свой диск, а приложение само реплицирует данные (Postgres, Kafka, ZooKeeper) — StatefulSet. Сам StatefulSet не делает базу отказоустойчивой: репликацию и failover реализует приложение или оператор.

    05 Жизненный цикл пода, пробы, завершение

    Здесь много вопросов «почему у меня теряются запросы при деплое» и «чем liveness отличается от readiness».

    Фазы и состояния

    Фаза пода: Pending (не назначен или скачивает образ) → Running → Succeeded или Failed. Также Unknown: нет связи с узлом. То, что показывает kubectl get pods в колонке STATUS (CrashLoopBackOff, ImagePullBackOff, OOMKilled), — это причины состояний контейнеров, а не фазы.

    Состав пода

    • Init-контейнеры выполняются последовательно до старта основных. Каждый должен завершиться успешно. Примеры: дождаться БД, прогнать миграции, скачать конфиг.
    • Sidecar-контейнеры: init-контейнер с restartPolicy: Always. Стабильны с версии 1.33. Стартуют до основных, работают всё время жизни пода и останавливаются после основных. Решают старую проблему, когда Job не завершался из-за работающего прокси-сайдкара.
    • pause-контейнер (sandbox) держит сетевой namespace пода. Поэтому IP не меняется при перезапуске контейнеров внутри пода.

    Пробы

    ПробаПри провалеДля чего
    startupProbeКонтейнер перезапускается после исчерпания попытокМедленный старт. Пока проба не прошла, liveness и readiness не выполняются.
    livenessProbeКонтейнер перезапускаетсяОбнаружить зависание: deadlock, процесс жив, но не работает.
    readinessProbeПод убирается из Endpoints, перезапуска нетВременно не принимать трафик: прогрев, перегрузка, недоступна зависимость.
    АнтипаттернLiveness-проба, которая проверяет базу данных. БД моргнула → все поды одновременно провалили liveness → массовый рестарт → холодный старт и шторм подключений → каскадный отказ. Liveness должна проверять только сам процесс. Зависимости можно учитывать в readiness, и то осторожно: если БД недоступна, все поды станут NotReady и сервис целиком пропадёт из балансировки.

    restartPolicy и CrashLoopBackOff

    Always (по умолчанию, обязательно для Deployment), OnFailure, Never. Контейнер перезапускает kubelet локально, тот же под на том же узле. Задержка между рестартами растёт экспоненциально: 10 с, 20 с, 40 с и далее до 5 минут. Это и есть CrashLoopBackOff: контейнер стартует и падает, kubelet ждёт перед следующей попыткой.

    Корректное завершение (graceful shutdown)

    При удалении пода (деплой, scale down, drain) происходит следующее, параллельно:

    1. Под получает deletionTimestamp и состояние Terminating.
    2. Ветка А: EndpointSlice-контроллер убирает под из эндпоинтов, kube-proxy, Ingress-контроллеры и балансировщики обновляют правила. Это занимает время: на разных узлах по-разному.
    3. Ветка Б: kubelet выполняет preStop-хук, затем отправляет SIGTERM процессу с PID 1 в контейнере.
    4. Через terminationGracePeriodSeconds (по умолчанию 30 с, отсчёт включает preStop) — SIGKILL.
    Почему теряются запросы при деплоеВетки А и Б идут одновременно. Приложение получает SIGTERM и закрывается раньше, чем все узлы перестали слать на него трафик. Отсюда ошибки 502 и connection refused. Решение: preStop: sleep 5–15, чтобы дать время на распространение изменений; приложение должно корректно обрабатывать SIGTERM, дорабатывать текущие запросы и закрывать соединения. Ещё одна классика: shell-обёртка sh -c "app" на месте PID 1 не передаёт SIGTERM приложению, и через 30 секунд его убивает SIGKILL. Решение: exec в entrypoint или tini.

    06 Ресурсы, QoS и планирование

    Здесь много практических вопросов: «почему под Pending», «почему OOMKilled», «почему тормозит при низкой загрузке CPU».

    requests и limits

    requestslimits
    Кто используетScheduler: на узле должно быть свободно столько ресурсов по сумме requests. Также cgroup-веса CPU.Ядро через cgroups при работе
    CPUГарантированная доля при конкуренцииПревышение приводит к троттлингу (CFS quota). Процесс не убивают, он замедляется.
    ПамятьУчитывается при планировании и вытесненииПревышение приводит к OOMKilled (exit code 137). Память нельзя «затроттлить».

    CPU измеряется в ядрах: 500m — полъядра. Память — в байтах: 256Mi. Scheduler смотрит на requests, а не на фактическое потребление. Узел может быть загружен на 10%, но если requests уже «раздали», новые поды туда не попадут.

    Классы QoS

    КлассУсловиеСудьба при нехватке памяти на узле
    GuaranteedУ всех контейнеров заданы requests = limits для CPU и памятиВытесняются последними
    BurstableЧто-то задано, но не GuaranteedПосередине. Первыми те, кто сильнее превысил свои requests
    BestEffortНичего не заданоВытесняются первыми
    Два разных механизма, их часто путаютOOMKilled — контейнер превысил свой лимит памяти, его убило ядро, kubelet перезапустит контейнер в том же поде. Evicted — на узле в целом закончились память, диск или PID. kubelet сам выселяет поды, чтобы спасти узел, и под пересоздаётся контроллером уже в другом месте.

    Распространённая практика: для памяти limit = request (предсказуемость). Для CPU многие не ставят limit или ставят с большим запасом, чтобы избежать троттлинга, особенно у многопоточных рантаймов (JVM, Go).

    LimitRange задаёт значения по умолчанию и минимумы-максимумы для контейнеров в namespace. ResourceQuota ограничивает суммарное потребление namespace. Если в namespace есть квота на CPU или память, поды без requests будут отклонены.

    Изменение ресурсов без пересоздания пода (in-place resize) появилось в новых версиях. Классическая модель: изменение ресурсов в шаблоне Deployment приводит к пересозданию подов.

    Как scheduler выбирает узел

    1. Фильтрация: отбросить узлы, где не хватает ресурсов по requests, не совпадает nodeSelector или affinity, есть taint без toleration, заняты нужные hostPort, недоступен том (зона диска).
    2. Оценка: ранжировать оставшиеся. Учитываются равномерность загрузки, предпочтения affinity, распределение по зонам, наличие образа на узле.
    3. Binding: записать выбранный узел в под. Если подходящих узлов нет, под остаётся Pending с событием FailedScheduling. Тогда может сработать preemption: вытеснение подов с более низким PriorityClass.

    Инструменты управления размещением

    МеханизмСмысл
    nodeSelectorПростое «только на узлы с меткой X»
    nodeAffinityТо же, но с выражениями. required… — жёсткое условие, preferred… — пожелание
    podAffinity / podAntiAffinityРазмещать рядом с подами X или подальше от них. Анти-аффинити по kubernetes.io/hostname разносит реплики по разным узлам
    taints и tolerationsTaint на узле отталкивает поды. Toleration на поде разрешает встать на такой узел, но не притягивает. Эффекты: NoSchedule, PreferNoSchedule, NoExecute (выгоняет и уже работающие поды). Пример использования: выделенные GPU-узлы, control plane
    topologySpreadConstraintsРавномерно распределить реплики по зонам или узлам (maxSkew). Основной способ пережить отказ зоны
    PriorityClassПриоритет при планировании и вытеснении
    Taint и affinity — не одно и то жеЧтобы выделить узлы под одну команду, нужны оба механизма. Taint не пускает чужих. Toleration плюс nodeAffinity приводят своих именно туда. С одной только toleration под может уехать на любой обычный узел.

    07 Сеть: модель, Service, DNS, Ingress

    Обязательная тема. Нужно понимать, где реально проходит пакет.

    Сетевая модель Kubernetes: три правила

    1. У каждого пода свой IP.
    2. Поды общаются с любыми подами на любых узлах без NAT.
    3. Агенты узла, например kubelet, могут обращаться ко всем подам на этом узле.

    Kubernetes только задаёт требования. Реализует их CNI-плагин: через overlay (VXLAN, Geneve), через маршрутизацию (BGP в Calico) или через eBPF (Cilium).

    Service: стабильный адрес для изменчивого набора подов

    Поды умирают и меняют IP. Service даёт постоянное имя и виртуальный IP и выбирает поды по label selector. Контроллер поддерживает EndpointSlice — список IP готовых подов.

    ТипКак работает
    ClusterIP (по умолчанию)Виртуальный IP, доступный только внутри кластера. Ни один процесс не слушает этот IP. kube-proxy на каждом узле прописал правила: пакет к ClusterIP:port заменяется (DNAT) на IP случайного готового пода. Поэтому ClusterIP не отвечает на ping.
    NodePortClusterIP плюс порт 30000–32767 на каждом узле
    LoadBalancerNodePort плюс внешний балансировщик облака (создаёт cloud-controller-manager)
    Headless (clusterIP: None)Виртуального IP нет. DNS возвращает IP всех подов напрямую. Используется со StatefulSet: db-0.db.ns.svc.cluster.local
    ExternalNameDNS CNAME на внешнее имя

    Путь пакета: под A → Service → под B

    1. Приложение резолвит payments. Файл /etc/resolv.conf в поде содержит search-домены (<ns>.svc.cluster.local и другие) и указывает на CoreDNS. CoreDNS возвращает ClusterIP.
    2. Пакет к ClusterIP перехватывается правилами iptables, IPVS или nftables на узле отправителя и получает DNAT на IP конкретного пода B.
    3. CNI доставляет пакет до узла с подом B по маршрутизации или через overlay.
    4. Ответ проходит обратное преобразование через conntrack.
    СледствияБалансировка происходит на уровне L4 при установке соединения, а не на уровне запросов. Долгоживущие соединения, например gRPC и HTTP/2, «прилипают» к одному поду, и нагрузка распределяется неравномерно. Для балансировки gRPC нужна клиентская балансировка через headless Service или service mesh. DNS-шаблон ndots:5 вызывает лишние DNS-запросы к внешним именам: известный источник задержек.

    Входящий трафик снаружи: Ingress и Gateway API

    Ingress — L7-маршрутизация HTTP по хосту и пути, TLS-терминация. Сам объект Ingress ничего не делает: нужен Ingress-контроллер (nginx, Traefik, HAProxy, облачный). Контроллер обычно стоит за Service типа LoadBalancer.

    Gateway API — более новый стандарт и преемник Ingress. Разделяет роли: GatewayClass (инфраструктура), Gateway (точка входа, принадлежит платформенной команде), HTTPRoute или GRPCRoute (маршруты, принадлежат командам сервисов). Поддерживает разделение трафика по весам (канарейки), заголовки, разные протоколы. Сообщество выводит из поддержки популярный ingress-nginx, поэтому вопрос о миграции на Gateway API сейчас актуален.

    NetworkPolicy

    По умолчанию все поды могут общаться со всеми. NetworkPolicy — это файрвол на уровне подов (L3/L4) по меткам, namespace и CIDR. Как только под попал под политику типа Ingress, всё входящее, что явно не разрешено, запрещается. Разрешения складываются, явного «deny» в базовом API нет. Политики работают, только если CNI их поддерживает: с Flannel объекты создадутся, но ничего не будут делать. Типичный подход: default-deny в namespace плюс явные разрешения. Не забудьте разрешить egress на DNS (порт 53).

    08 Хранилище: Volume, PV, PVC, StorageClass

    Вопросы обычно о том, как данные переживают пересоздание пода и почему под не может подключить диск.

    Файловая система контейнера эфемерна: при рестарте контейнера всё, что записано вне томов, пропадает.

    СущностьСмысл
    Volume в подеЖивёт вместе с подом: emptyDir (временный, общий для контейнеров пода), configMap, secret, projected, hostPath (каталог узла, опасно)
    PersistentVolume (PV)Реальный диск в кластере (EBS, Ceph RBD, NFS). Объект уровня кластера
    PersistentVolumeClaim (PVC)Заявка пода: «мне нужно 10Gi, RWO, класса fast». Объект namespace
    StorageClassШаблон для динамического создания PV: провижинер (CSI-драйвер), параметры, reclaimPolicy, volumeBindingMode
    CSIСтандартный интерфейс драйверов хранилища: создать, подключить к узлу, смонтировать, сделать снапшот, расширить

    Схема: под ссылается на PVC → PVC связывается с PV (существующим или созданным через StorageClass) → CSI подключает диск к узлу и монтирует в под.

    Режимы доступа

    • RWO (ReadWriteOnce) — чтение и запись с одного узла. Блочные диски: EBS, GCE PD.
    • ROX — чтение с многих узлов. RWX — запись с многих узлов, нужен NFS или CephFS. RWOP — строго один под.

    Важные детали

    • reclaimPolicy: Delete (по умолчанию для динамических): удалили PVC — удалился диск с данными. Retain — диск остаётся.
    • volumeBindingMode: WaitForFirstConsumer: диск создаётся после того, как scheduler выбрал узел. Иначе диск может появиться в зоне A, а под — оказаться в зоне B.
    • Облачный блочный диск привязан к зоне. Под с таким PVC можно перепланировать только в ту же зону.
    • PVC от volumeClaimTemplates StatefulSet не удаляются при удалении или масштабировании StatefulSet по умолчанию. Это защищает данные.

    09 Конфигурация и безопасность

    ConfigMap, Secret и RBAC спрашивают почти всегда. Также часто спрашивают, насколько секреты на самом деле секретны.

    ConfigMap и Secret

    Передаются в под как переменные окружения или как файлы в томе.

    • Secret — это base64, а не шифрование. В etcd он по умолчанию лежит в открытом виде. Нужно настроить encryption at rest (EncryptionConfiguration, лучше с KMS), ограничить доступ через RBAC (право list secrets раскрывает все секреты namespace), использовать внешние хранилища: Vault, External Secrets Operator, Secrets Store CSI.
    • Secret в поде монтируется в tmpfs, то есть в память, а не на диск узла.
    • Размер ConfigMap или Secret — до 1 МиБ.

    Аутентификация и авторизация

    • Пользователей в Kubernetes нет как объектов. Людей аутентифицируют снаружи: сертификаты, OIDC.
    • ServiceAccount — учётная запись для процессов в подах. Под получает короткоживущий токен (projected, с аудиторией и сроком жизни), с которым ходит в API. Этот же токен используется для workload identity в облаках (IRSA, Workload Identity).
    • RBAC: Role (права в namespace) или ClusterRole (права в кластере), связка через RoleBinding или ClusterRoleBinding. Правило: какие действия (get, list, watch, create, update, patch, delete) с какими ресурсами разрешены. Права только разрешающие, запретов нет. ClusterRole можно привязать через RoleBinding: тогда права действуют только в одном namespace.
    • Проверить права: kubectl auth can-i delete pods --as=system:serviceaccount:ns:sa.

    Admission

    Цепочка из этапа 3: mutating → validating. Механизмы политик: вебхуки (OPA Gatekeeper, Kyverno), встроенные ValidatingAdmissionPolicy на CEL без внешнего сервиса, Pod Security Admission с уровнями privileged, baseline, restricted через метки namespace. PSA заменил удалённые PodSecurityPolicy.

    Риск вебхуковЕсли admission-вебхук с failurePolicy: Fail недоступен, API отклоняет все подпадающие запросы. Можно заблокировать создание подов во всём кластере, включая поды самого вебхука. Исключайте системные namespace и следите за таймаутами.

    Безопасность пода

    securityContext: runAsNonRoot, readOnlyRootFilesystem, allowPrivilegeEscalation: false, capabilities.drop: [ALL], seccomp-профиль RuntimeDefault. Опасно: privileged: true, hostPath, hostNetwork, hostPID, токен ServiceAccount с широкими правами. На практике каждый из них означает путь к захвату узла.

    10 Деплой, откат, масштабирование

    Как обновить без простоя и как кластер растёт под нагрузкой.

    RollingUpdate в Deployment

    • maxSurge — сколько подов сверх replicas можно создать во время обновления (по умолчанию 25%).
    • maxUnavailable — сколько подов могут быть недоступны (по умолчанию 25%). Оба параметра не могут быть 0 одновременно.
    • Новый RS масштабируется вверх, старый вниз. Шаг засчитывается, только когда новые поды Ready. Поэтому без readinessProbe rolling update «проходит» даже с нерабочей версией.
    • minReadySeconds — сколько под должен простоять Ready, чтобы считаться доступным. progressDeadlineSeconds — после этого срока Deployment помечается как зависший, но автоматического отката нет.
    • Стратегия Recreate: сначала удалить все старые поды, потом создать новые. Простой есть, зато две версии не работают одновременно.
    • Откат: kubectl rollout undo deployment/api возвращает шаблон предыдущего RS. Статус: kubectl rollout status.

    Blue/green и canary встроенным Deployment напрямую не реализуются. Варианты: два Deployment и переключение селектора Service; веса в Gateway API, Ingress или service mesh; Argo Rollouts или Flagger с автоматическим анализом метрик.

    Автомасштабирование: три уровня

    ЧтоМасштабируетКак
    HPAЧисло репликdesired = ceil(current × текущая_метрика / целевая). Метрики: CPU и память (через metrics-server, процент считается от requests), custom и external (Prometheus Adapter, KEDA). Цикл около 15 с. Стабилизация scale-down по умолчанию 5 минут, чтобы реплики не скакали.
    VPArequests и limitsРекомендует или выставляет ресурсы по истории потребления. Не стоит использовать одновременно с HPA по той же метрике CPU или памяти.
    Cluster Autoscaler / KarpenterЧисло узловДобавляет узлы, когда есть Pending-поды, которые не помещаются (не по загрузке CPU узлов!). Удаляет недогруженные узлы, если их поды можно переселить.
    Цепочка при пике нагрузкиРастёт CPU → HPA увеличивает число реплик → новые поды не помещаются и висят в Pending → Cluster Autoscaler заказывает узел (минуты) → поды запускаются. Отсюда практики: запас ресурсов (overprovisioning с низким приоритетом), быстрый старт приложений, корректные requests.

    PodDisruptionBudget (PDB) — «не больше N подов одновременно недоступны» (или «не меньше M доступны»). Защищает только от добровольных нарушений: drain, обновление узлов, autoscaler. От падения узла PDB не защищает.

    11 Расширяемость: CRD, операторы, GitOps

    Показывает, что вы понимаете Kubernetes как платформу, а не как «запускалку контейнеров».

    • CRD (CustomResourceDefinition) добавляет в API новый тип объектов, например PostgresCluster. API-сервер хранит такие объекты, валидирует по OpenAPI-схеме и раздаёт watch, как для встроенных типов.
    • Оператор = CRD + свой контроллер, в который зашиты знания администратора: как развернуть кластер БД, сделать failover, бэкап, обновление. Работает по тому же циклу согласования. Примеры: CloudNativePG, Strimzi (Kafka), Prometheus Operator, cert-manager.
    • Finalizers — метки в metadata.finalizers, которые не дают удалить объект, пока контроллер не выполнит очистку (например, удалит облачный балансировщик). Если контроллер мёртв, объект навсегда зависает в Terminating.
    • GitOps (Argo CD, Flux): желаемое состояние лежит в Git, агент в кластере постоянно согласует кластер с репозиторием. Это тот же цикл согласования, поднятый на уровень выше. Ручные правки через kubectl edit будут отменены.
    • Helm — шаблонизатор и менеджер релизов манифестов. Kustomize — наложение патчей без шаблонов, встроен в kubectl.

    12 Kubernetes как распределённая система

    Вопросы про консенсус, кворум, отказ узлов и split brain отличают сильного кандидата. Здесь всё сходится вместе.

    etcd, Raft и кворум

    • Raft: один лидер принимает записи и реплицирует их фолловерам. Запись подтверждается, когда её сохранило большинство (кворум = ⌊n/2⌋ + 1).
    • 3 узла переживают отказ 1, 5 узлов — отказ 2. Чётное число бессмысленно: 4 узла тоже переживают только 1 отказ, а кворум больше. Больше 5–7 узлов замедляют запись: нужно больше подтверждений.
    • При сетевом разделении сторона с меньшинством не может писать. Это защита от split brain. В терминах CAP etcd выбирает согласованность (CP).
    • etcd чувствителен к задержке диска (fsync) и сети. Медленный диск приводит к перевыборам лидера и задержкам всего API. Для etcd нужны быстрые SSD и малые RTT между членами, обычно в пределах региона.
    • По умолчанию размер базы ограничен (квота около 2 ГиБ, рекомендуемый максимум 8 ГиБ). При превышении etcd переходит в режим «только чтение и удаление» (alarm NOSPACE). Нужны compaction и defrag. Множество объектов, например тысячи Events или старых ReplicaSet, раздувают базу.
    • Бэкап: etcdctl snapshot save. Это и есть бэкап состояния кластера. Данные в PV туда не входят.

    HA control plane

    • API-серверы — несколько штук за балансировщиком, все активны: у них нет состояния.
    • Scheduler и controller-manager — несколько копий, но активна одна. Выбор лидера через объект Lease: лидер периодически продлевает аренду. Если перестал, после истечения срока лидерство берёт другая копия. Это защищает от двух одновременно действующих контроллеров.
    • Топологии: etcd на тех же узлах, что control plane (stacked), или отдельный кластер etcd (external).

    Согласованность и асинхронность

    • Запись в API строго согласована. Но реакция системы асинхронна и в конечном счёте согласована (eventual consistency): контроллеры, kubelet и kube-proxy догоняют состояние с задержкой. В течение какого-то времени разные узлы видят разные Endpoints.
    • Кеши информеров могут отставать. Контроллеры обязаны быть идемпотентными и терпеть конфликты 409.
    • Отсутствие центрального «оркестратора команд» означает отсутствие единой точки, которая должна быть жива, чтобы приложения работали. Data plane (поды, правила сети) продолжает работать без control plane.

    Отказ узла: хронология

    1. kubelet перестаёт обновлять Lease узла: сеть пропала, узел умер, kubelet завис.
    2. Через node-monitor-grace-period (порядка 40–50 секунд, зависит от версии) Node controller ставит узлу Ready=Unknown и taint node.kubernetes.io/unreachable:NoExecute.
    3. Поды по умолчанию имеют toleration к этому taint на 300 секунд. Через ~5 минут их помечают на удаление.
    4. Поды Deployment и ReplicaSet пересоздаются на других узлах. Итого около 5–6 минут без реплик с этого узла. Для критичных сервисов toleration можно уменьшить, но рискуете лишними пересозданиями при сетевых «морганиях».
    5. Поды StatefulSet автоматически не пересоздаются. Они висят в Terminating или Unknown, пока узел не вернётся, объект Node не удалят или не выполнят force delete. Причина: StatefulSet гарантирует не больше одного пода db-0. Kubernetes не знает, умер узел или просто отрезан сетью, а два db-0 на одном диске — повреждение данных. Для явного подтверждения есть taint node.kubernetes.io/out-of-service (non-graceful node shutdown).
    Split brain на уровне приложенияЕсли узел отрезан сетью, но жив, его контейнеры продолжают работать. kubelet не может узнать, что их «удалили». Deployment поднимет замены, и какое-то время будут работать обе копии. Для stateless-сервисов это допустимо. Для лидера, который пишет в общий ресурс, это опасно. Поэтому приложениям с единственным лидером нужен собственный механизм: fencing, Lease с проверкой, консенсус.

    13 Сценарии «что будет, если…»

    Именно так проверяют понимание. Сначала ответьте сами, потом раскройте ответ. Логика почти всегда одна: какой контроллер видит какое расхождение и что он делает.

    Отказы компонентов

    Упали все API-серверы

    Работающие поды продолжают работать, Service работают: правила iptables остаются на узлах. kubelet продолжает локально перезапускать упавшие контейнеры. Но: не работает kubectl, не создаются и не планируются новые поды, не обновляются Endpoints (умерший под остаётся в балансировке), не работает HPA, не обрабатываются отказы узлов. Кластер «заморожен» в последнем состоянии. Data plane отделён от control plane.

    etcd потерял кворум (например, 2 из 3 узлов недоступны)

    Записи невозможны. API-сервер отдаёт ошибки, в том числе на большую часть чтений: по умолчанию нужно строго согласованное чтение. Последствия такие же, как при падении API: нагрузки работают, изменения невозможны. Восстановление: вернуть узлы или восстановить кластер etcd из snapshot. Всё, что изменилось после snapshot, будет потеряно, и контроллеры начнут приводить мир к старому состоянию.

    Упал scheduler

    Новые поды висят в Pending без узла. Уже назначенные поды работают. Масштабирование и деплой «застрянут» на этапе планирования. При HA лидерство возьмёт другая копия через Lease.

    Упал controller-manager

    Ничего не согласуется: Deployment не создаёт ReplicaSet, удалённые поды не пересоздаются, отказы узлов не обрабатываются, Endpoints не обновляются, Job не создают поды, сборка мусора не идёт. Уже работающее продолжает работать.

    Остановился kubelet на одном узле

    Контейнеры на узле продолжают работать: ими управляет containerd. Но статус не обновляется, пробы не выполняются. Через ~40–50 секунд узел станет NotReady, ещё через ~5 минут поды будут выселены и пересозданы в другом месте. Возможен период, когда старые копии ещё работают. Если поды остались в Endpoints, трафик может идти на них до того, как узел станет NotReady.

    Остановился kube-proxy на узле

    Существующие правила остаются, поэтому трафик пока ходит. Но изменения Service и Endpoints на этом узле больше не применяются: поды этого узла могут слать запросы на уже удалённые IP. Деградация постепенная и трудно заметная.

    Упал CoreDNS

    Новые разрешения имён внутри кластера перестают работать. Обращения по IP и уже закешированные соединения работают. Почти все сервисы ходят по именам, поэтому последствия заметные. CoreDNS обычно запускают в 2+ репликах и часто добавляют NodeLocal DNSCache.

    Сетевое разделение: часть узлов отрезана от control plane, но друг с другом связана

    Поды на отрезанных узлах продолжают работать и обслуживать трафик, который до них доходит. Control plane считает узлы Unreachable и через ~5 минут пересоздаёт поды Deployment на доступных узлах. Получаются две копии. Поды StatefulSet не пересоздаются. Когда связь восстановится, kubelet увидит, что поды удалены, и остановит их.

    Изменения объектов

    Удалить под, которым управляет Deployment

    ReplicaSet увидит 2 пода вместо 3 и создаст новый, с новым именем и новым IP. Удаление пода — обычный способ «перезапустить» его.

    Удалить ReplicaSet, которым управляет Deployment

    Сборщик мусора удалит его поды, Deployment создаст новый RS с тем же шаблоном, тот создаст поды. Будет короткий простой. Удаление с --cascade=orphan оставит поды, а новый RS «усыновит» их по меткам.

    Изменить метку пода так, чтобы она перестала совпадать с селектором ReplicaSet

    Под перестаёт быть «своим»: ReplicaSet создаст замену, а изменённый под останется работать сам по себе и выпадет из Service. Это известный приём отладки: вывести под из ротации, не убивая его, чтобы исследовать.

    Изменить selector у Deployment

    В apps/v1 селектор неизменяем: API вернёт ошибку. Нужно пересоздать Deployment.

    Изменить образ в Deployment

    Меняется шаблон пода → новый хеш → новый ReplicaSet → rolling update по maxSurge и maxUnavailable. Изменение только replicas шаблон не меняет и нового RS не создаёт.

    Изменить ConfigMap, который использует приложение

    Поды не перезапускаются. Переменные окружения не обновятся до перезапуска пода. Файлы в смонтированном томе обновятся через некоторое время (обычно до минуты, синхронизация kubelet и кеш), но приложение должно само их перечитать. При монтировании через subPath файл не обновится никогда. Практика: kubectl rollout restart, аннотация с хешем конфига в шаблоне пода (паттерн Helm) или неизменяемые ConfigMap с версией в имени.

    Вручную изменить replicas, когда настроен HPA

    HPA на следующем цикле вернёт своё значение. Под управлением HPA нельзя задавать replicas в манифесте GitOps: иначе GitOps и HPA будут спорить. Поле убирают из манифеста.

    Сделать kubectl edit ресурса, которым управляет Argo CD или Flux

    Правку откатят при следующей синхронизации (если включён self-heal), либо приложение будет показано как OutOfSync. Правильный путь — коммит в Git.

    Указать requests больше, чем есть у любого узла

    Под навсегда Pending, событие FailedScheduling: Insufficient cpu. Cluster Autoscaler тоже не поможет, если ни один тип узлов в группах не подходит.

    Убрать readinessProbe

    Под считается Ready сразу после старта контейнера. Трафик пойдёт до того, как приложение прогрелось. При rolling update старые поды удалятся, даже если новая версия не работает: простой и ошибки.

    Поставить слишком агрессивную livenessProbe (маленький timeout, без startupProbe)

    При медленном старте или GC-паузе под убивается до того, как станет готов → CrashLoopBackOff. Под нагрузкой убиваются перегруженные поды, нагрузка падает на остальные, и они тоже начинают падать.

    Контейнер превысил memory limit

    Ядро убивает процесс, статус OOMKilled, exit code 137, kubelet перезапускает контейнер на том же узле. Если это повторяется — CrashLoopBackOff. Под не переезжает и не выселяется.

    На узле закончилось место на диске

    kubelet ставит условие DiskPressure и taint, сначала чистит неиспользуемые образы и мёртвые контейнеры, затем выселяет поды (начиная с BestEffort). Поды получают статус Evicted, контроллеры пересоздают их на других узлах.

    kubectl drain узла, а у сервиса PDB minAvailable равен числу реплик

    Drain зависнет: Eviction API будет отказывать (429), потому что любое выселение нарушит бюджет. То же самое, если реплика одна, а maxUnavailable: 0. Это частая причина зависших обновлений узлов.

    Удалить namespace

    Удаляется всё внутри: поды, сервисы, секреты, PVC (а значит и диски при reclaimPolicy: Delete). Если внутри есть объекты с финализаторами, контроллер которых уже удалён, namespace зависнет в Terminating.

    Объект застрял в Terminating

    Почти всегда виноват финализатор, который никто не снимает. У пода причиной может быть недоступный узел (kubelet не подтверждает удаление). Решение: починить контроллер или узел. Крайний вариант: снять финализатор вручную или выполнить --force --grace-period=0, понимая риски (неочищенные внешние ресурсы, две копии пода StatefulSet).

    Использовать тег :latest

    Для :latest imagePullPolicy по умолчанию Always, для других тегов IfNotPresent. Разные узлы могут запустить разные фактические версии. Деплой не произойдёт при пуше нового latest: шаблон не изменился. Откат бессмыслен. Используйте неизменяемые теги или digest.

    Под StatefulSet с PVC на RWO-диске пытается запуститься на другом узле

    Пока диск подключён к старому узлу, будет ошибка Multi-Attach error. Если диск в другой зоне — Pending из-за volume node affinity. Поэтому для StatefulSet важно распределение по зонам и понимание, что под «привязан» к зоне своего диска.

    Сервис есть, но запросы к нему не проходят

    Проверка по цепочке: совпадает ли selector Service с метками подов (kubectl get endpointslices — пусто?), готовы ли поды (readiness), правильный ли targetPort, слушает ли приложение 0.0.0.0, а не 127.0.0.1, нет ли NetworkPolicy, резолвится ли DNS.

    14 Диагностика: алгоритм и команды

    Часто дают задачу «под не стартует, что будешь делать». Ответ должен быть последовательным.

    Алгоритм

    1. kubectl get pods -o wide — статус, рестарты, узел.
    2. kubectl describe pod <name> — Events внизу: ошибки планирования, скачивания образа, проб, монтирования томов. Это самый информативный шаг.
    3. kubectl logs <pod> [-c container] [--previous] — --previous показывает логи предыдущего упавшего контейнера.
    4. kubectl get events --sort-by=.lastTimestamp -n ns.
    5. kubectl exec -it или kubectl debug (эфемерный отладочный контейнер, полезно для distroless-образов).
    6. Узел: kubectl describe node (Conditions, Allocated resources), kubectl top.

    Статус → причина

    СтатусКуда смотреть
    PendingНе хватает ресурсов по requests, taint без toleration, affinity, не создаётся PVC, квота
    ImagePullBackOff / ErrImagePullОпечатка в образе или теге, нет доступа к registry (imagePullSecrets), rate limit
    CrashLoopBackOffПриложение падает при старте: logs --previous, конфиг, отсутствующий секрет, неверная команда, liveness
    OOMKilledЛимит памяти мал или утечка. Для JVM: размер heap относительно лимита
    CreateContainerConfigErrorНет ConfigMap или Secret, на который ссылается под
    Running, но 0/1 ReadyНе проходит readinessProbe
    EvictedДавление ресурсов на узле
    Terminating навсегдаФинализаторы, недоступный узел

    Полезные команды

    kubectl explain deployment.spec.strategy        # документация по полям
kubectl get deploy api -o yaml                  # фактический объект
kubectl rollout status|history|undo deploy/api
kubectl rollout restart deploy/api              # пересоздать поды
kubectl scale deploy/api --replicas=5
kubectl port-forward svc/api 8080:80
kubectl auth can-i list secrets -n prod
kubectl get endpointslices -l kubernetes.io/service-name=api
kubectl cordon|uncordon|drain node-1 --ignore-daemonsets
kubectl top pods --containers

    15 Эксплуатация и экосистема

    Короткий обзор, чтобы поддержать разговор о продакшене.

    • Обновление кластера: сначала control plane, затем узлы. Kubelet может отставать от API-сервера на несколько минорных версий, но не опережать его. Минорные версии обновляют по одной. Узлы обновляют через cordon → drain → обновление → uncordon или заменой групп узлов.
    • Наблюдаемость: Prometheus (метрики, kube-state-metrics, node-exporter), Grafana, логи через DaemonSet-агент (Fluent Bit, Vector) в Loki или Elasticsearch, трейсы через OpenTelemetry.
    • Service mesh (Istio, Linkerd, Cilium): mTLS между сервисами, ретраи, таймауты, балансировка L7, канарейки, телеметрия. Ценой дополнительной сложности и задержки.
    • Managed-кластеры (EKS, GKE, AKS, Yandex Managed Kubernetes): провайдер управляет control plane и etcd, вы управляете узлами и нагрузками.
    • Мультиарендность: namespace + RBAC + ResourceQuota + NetworkPolicy + Pod Security. Для жёсткой изоляции — отдельные кластеры или узлы.
    • Лимиты масштаба (ориентиры из документации): до ~5000 узлов, ~110 подов на узел по умолчанию, ~150 000 подов в кластере.

    16 Самопроверка: вопросы с собеседований

    Ответьте вслух, затем раскройте. Если ответ не складывается в 2–3 фразы, вернитесь к соответствующему этапу.

    Чем Pod отличается от контейнера? Зачем несколько контейнеров в поде?

    Pod — группа контейнеров с общей сетью и томами, всегда на одном узле, минимальная единица планирования. Несколько контейнеров нужны для тесно связанных процессов: sidecar-прокси, сборщик логов, init-подготовка. Независимые сервисы — в разные поды.

    Чем Deployment отличается от StatefulSet и DaemonSet?

    Deployment — взаимозаменяемые реплики. StatefulSet — стабильные имена, DNS и свой том у каждой реплики, упорядоченность, не больше одного экземпляра на идентичность. DaemonSet — по поду на узел.

    Как работает Service, если ClusterIP никто не слушает?

    kube-proxy на каждом узле создаёт правила iptables, IPVS или nftables, которые DNAT-ят пакеты с ClusterIP на IP подов из EndpointSlice. Перехват происходит на узле отправителя.

    Liveness и readiness: разница?

    Провал liveness — перезапуск контейнера. Провал readiness — исключение из Endpoints без перезапуска. Startup откладывает обе пробы до успешного старта.

    requests и limits, что будет при превышении?

    requests нужны для планирования и гарантий. При превышении CPU limit — троттлинг, при превышении memory limit — OOMKill. Классы QoS определяют порядок вытеснения.

    Почему под в Pending?

    Нет узла с достаточными свободными requests, taint без toleration, неподходящие affinity или nodeSelector, PVC не привязался, ограничение квоты. Смотреть Events в describe.

    Что хранится в etcd и почему его кластер нечётного размера?

    Всё состояние объектов кластера. Raft требует кворум ⌊n/2⌋+1. Нечётное число даёт максимальную отказоустойчивость на узел: 3 → 1 отказ, 5 → 2.

    Как обеспечить zero-downtime деплой?

    RollingUpdate с maxUnavailable: 0 или небольшим значением, корректная readinessProbe, preStop sleep и обработка SIGTERM, достаточный terminationGracePeriod, несколько реплик, PDB, распределение по узлам и зонам, обратно совместимые миграции БД.

    Как приложение в поде получает доступ к облачному API без статических ключей?

    Через ServiceAccount и workload identity: projected-токен SA обменивается у провайдера на временные облачные учётные данные (IRSA, GKE Workload Identity).

    Как ограничить сетевой доступ между сервисами?

    NetworkPolicy (при поддержке CNI): default-deny и явные разрешения по меткам и namespace. Для L7 и mTLS — service mesh или политики Cilium.

    Что такое оператор и зачем он нужен?

    CRD плюс контроллер, который автоматизирует эксплуатацию сложного, обычно stateful, приложения по модели согласования: развёртывание, failover, бэкапы, обновления.

    Почему Kubernetes называют level-triggered и почему это важно?

    Контроллеры реагируют на текущее состояние, а не на конкретное событие. Пропущенное событие, рестарт или сбой не ломают систему: при следующем цикле расхождение будет найдено и исправлено.

    Что происходит при отказе узла и сколько это длится?

    ~40–50 с до NotReady, ещё 300 с toleration до выселения, затем пересоздание подов Deployment. Около 5–6 минут. Поды StatefulSet требуют подтверждения, что узел мёртв.

    Как HPA вычисляет число реплик? Почему без requests не работает?

    ceil(текущие_реплики × текущая/целевая). Утилизация CPU считается в процентах от requests: без requests процент не определён.

    Secret защищён?

    По умолчанию нет: base64 и открытый вид в etcd. Нужны encryption at rest с KMS, строгий RBAC, по возможности внешнее хранилище секретов.

    Как два компонента контроллера не выполняют работу одновременно?

    Выбор лидера через Lease с периодическим продлением. Изменения объектов защищены оптимистической блокировкой через resourceVersion.

    Ingress и Gateway API?

    Оба описывают L7-входящий трафик, реализуются контроллером. Gateway API — новее, с разделением ролей (GatewayClass, Gateway, Route), весами, большим числом протоколов и переносимыми расширениями.

    Что будет с подами, если упадёт весь control plane?

    Продолжат работать. Kubelet перезапускает упавшие контейнеры локально, сеть работает по уже настроенным правилам. Не будет изменений, планирования, реакции на отказы и обновления Endpoints.

    17 Шпаргалка за 5 минут до собеседования

    Модель

    Desired state в etcd → контроллеры через watch → reconcile. Level-triggered, идемпотентно, всё через API-сервер.

    Control plane

    apiserver (вход, authn/authz/admission, единственный доступ к etcd), etcd (Raft, кворум), scheduler (filter → score → bind), controller-manager (циклы согласования, leader election).

    Узел

    kubelet (поды через CRI, пробы, статус, Lease), runtime (containerd), kube-proxy (правила Service), CNI (IP подов), CSI (диски).

    Цифры

    Grace period 30 с. Отказ узла ~40–50 с + 300 с. maxSurge и maxUnavailable 25%. NodePort 30000–32767. Backoff до 5 мин. Кворум ⌊n/2⌋+1. OOM = exit 137.

    Пробы

    liveness → рестарт. readiness → из Endpoints. startup → защищает медленный старт.

    Ресурсы

    requests → планирование. CPU limit → троттлинг. Memory limit → OOMKill. QoS: Guaranteed / Burstable / BestEffort.

    Сеть

    IP на под, без NAT. Service = виртуальный IP + DNAT. Headless → IP подов. Ingress / Gateway → L7. NetworkPolicy по умолчанию всё разрешает.

    Распределённость

    CP-хранилище, eventual consistency реакций, data plane живёт без control plane, при разделении сети возможны дубли, StatefulSet ждёт подтверждения.

    Как отвечать на «что будет, если…»1) Какой объект изменился или какой компонент отказал. 2) Какой контроллер это видит. 3) Какое расхождение желаемого и фактического он обнаружит и что сделает. 4) Что продолжит работать (data plane) и что остановится (control plane). 5) Как это заметить и починить.
